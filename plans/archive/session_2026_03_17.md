## 2. Diagnosed Why recall-text Is Flat

**Key finding:** The CA *does* encode propositional content. Attractor similarity
between near-paraphrase pairs is 0.51–0.56; same-domain-different-fact is 0.13;
cross-domain is 0.002–0.05. A 4× gap exists between "near-duplicate" and
"topically related."

**Why MMLU still fails:** The recall-text mode queries test questions against
stored dev/validation facts. These are *distinct* questions, not paraphrases.
Retrieval similarity stays in the 0.13 range (same-domain noise), not the
0.5+ range needed for reliable letter voting.

The benchmark failure is a **data mismatch**, not an architecture failure.

## 5. Performance Engineering — Crystallization Pipeline

### Problem
`wheeler-crystallize` was single-threaded. Profiling revealed:

| Stage | Time (batch=64) | Notes |
|-------|-----------------|-------|
| Embedding (sentence-transformer) | 2.65s | CPU, 20 threads — worst config |
| CA evolution | 0.071s | Already GPU-dispatched via HIP |
| `store_memory` (per-item) | 80–300ms and growing | O(n) JSON read+write |

### CPU Topology Discovered
- P-cores: CPUs 0–7 (5400–5500 MHz)
- E-cores: CPUs 8–19 (4600 MHz, in clusters of 4 sharing L2)

**Counterintuitive result:** E-cores outperform P-cores for embedding (1.2ms vs
1.4ms per text) because PyTorch GEMM reductions benefit from cluster-shared L2.
20 threads across all cores was the *worst* setting (22ms/text) due to
cross-cluster synchronization overhead.

### Fix 1 — Hardware-aware Pipeline (`wheeler_memory/crystallization.py`)

Three-stage pipelined architecture:
- **Embed thread → E-cores (12t):** `embed_to_frame_batch`, 12 OMP threads
- **Main thread → P-cores (GPU dispatch):** `evolve_and_interpret` via HIP
- **Store thread → E-cores:** sequential index writes

Core detection is automatic via `/sys/devices/system/cpu/cpuX/cpufreq/cpuinfo_max_freq`.

### Fix 2 — Batch Index Writes (`wheeler_memory/storage.py`)

Added `batch_store_memories()`: acquires index lock once per chunk, writes
all N entries, releases. Replaces N individual `store_memory()` calls.

**Throughput before/after:**
- Before: ~200 memories/min (O(n) JSON per item, n=3000+)
- After: ~16,000 memories/min (one JSON write per batch of 128)
- **~80× speedup**

SciQ (9,444 new facts): 57.6s. ARC (7,787 facts): 29.4s.

## 6. Associative Memory Characterization Benchmark

**File:** `scripts/bench_associative.py`

Three tests against published baselines:

| Test | Method |
|------|--------|
| Capacity curve | Recall % vs N stored, multiple trials with random subsets |
| Cue degradation | Recall % vs % words removed from query (0–70%) |
| Interference | Same-subject vs cross-subject store, physics query target |

**Results (N ≤ 50, α ≤ 0.012):**

| Test | Wheeler | Classical Hopfield | Modern Hopfield |
|------|---------|-------------------|-----------------|
| Capacity (N=50) | 100% | degrades above α=0.138 | exp(αN) |
| Cue degradation (70% removed) | 100% | ~50% at 30% corruption | >90% at 40% |
| Interference | 0% effect | significant | minimal |

**Caveat:** All tests are far below the classical capacity limit (α=0.012 vs
limit of 0.138). The degradation region is N=400–600. MMLU dev/val only
provides 69 facts — need SciQ to push into the stress zone.

## 7. System Architecture Diagnosis

**What Wheeler has:** hippocampus (storage + associative recall)
**What Wheeler lacks:** cortex (reasoning, composition, generation)

The CA settles into an attractor but the attractor doesn't generate language
or inference — it just sits as a pattern. The `decode` mode outsources
"thinking" to Ollama. `generation.py` exists but its role is unclear.

**Scale reality check:**
- 64×64 grid = 4,096 cells
- Classical reliable capacity: ~565 patterns (α=0.138)
- We stored 22,953 (40× over capacity) → explains noisy recall in benchmarks
- Scaling to 256×256 would give ~9k reliable patterns; 1024×1024 → ~140k
